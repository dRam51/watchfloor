# Watchfloor M2 — Dedupe and Scoring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Query the database and find the top items are genuinely the ones I'd have picked.

**Architecture:** A scoring pass separate from ingest. Clustering groups near-duplicate coverage; a mechanical scorer combines source trust, cluster size, and interest-profile matches into decay-invariant components; recency decay is applied **at read time** rather than baked into stored rows. Hard overrides bypass the computed score entirely.

**Tech Stack:** TypeScript, Node 26, `node:sqlite`, `yaml`, `zod`, vitest. No new dependencies expected.

## Global Constraints

Every task's requirements implicitly include this section.

- **Node 26.** No new runtime dependency without justification recorded in the task report.
- **Never delete anything.** No `rm`, no history rewrites, no `fs.rm`/`unlink`/`rmdir`. Obsolete files go to `attic/` via `git mv`. **Never edit an applied migration** — new schema is a new migration.
- **`items`, `item_scores`, and `item_clusters` are append-only**, enforced by triggers. A rescore appends; it never updates.
- **The markets beat is a research feed.** No sentiment, no directional label, no price target, no position size, no field whose name implies a recommendation. Relevance scoring means *whether I'd want to read it* — that is the only kind of score permitted.
- **This repository is public.** `docs/brief.md` and `config/portfolio.yaml` are gitignored and must never be committed.
- **Zero absolute paths.** Explicit `.ts` extensions. `npm run typecheck` and `npm run check:portability` clean.
- **No mocks, no network in tests.** Real temp-file SQLite, real fixtures.
- Commit after every passing test run. Never rewrite history. Branchless on `main`.

## The decision that shapes everything: decay at read time

§5 makes recency decay part of the score. §5.1 makes half-lives per-`item_type` for markets and per-beat elsewhere. But `item_scores` is **append-only**, and a decaying score changes continuously — so storing a decayed value would mean appending a new row per item per beat on every pass, forever, to record nothing but the passage of time.

**So: store the decay-invariant components; apply decay when reading.** A stored row carries source trust, cluster size at scoring time, interest matches, and the classification inputs. The query multiplies by a decay factor computed from `published_at` and the reader's `now`.

Consequences, all of them intended:

- One row per `(item_id, beat)` per genuine scoring event — a rescore happens when the interest profile changes or clustering revises, not when the clock moves.
- Ranking is correct at any instant without a background job.
- **A historical query is truthful**: asking "what would have ranked top last Tuesday" applies Tuesday's decay to the components known then, rather than replaying today's ranking backwards. This matters for the same reason the `as_of` work in M0 did.

## Two scores, never blended

§5.1 requires `signal_score` and `read_score` computed independently on every item, never collapsed into one number.

- **`signal_score`** — machine relevance. Novelty, materiality, entity match, timeliness. **Sharp decay, half-life in hours.** Filings and rule changes rank high; essays rank near zero.
- **`read_score`** — human interest. Source depth, explanatory value, primary-source-ness, non-duplication against what has already been read. **Slow decay, half-life in weeks**, and long-form must not fall off a two-week cliff.

Both are computed for **all six beats**, not just markets — the schema already keys scores on `(item_id, beat)`, the cost is negligible, and only the markets lane surfaces the dual view in the UI. Items scoring high on both are rare and disproportionately valuable; flag them.

## What M1 handed forward

Four findings from the first live ingest bear directly on this milestone.

**Cluster size is the dominant signal for US news** and this is where it gets tested for real. A story carried by AP *and* NPR *and* PBS is national news almost by definition.

**arXiv cross-listing shadows beats.** 18 papers appeared in both `cs.AI` and `cs.CR` with identical URLs, so identical `item_key`s. They are genuinely the same paper, but only the last-inserted row's beats survive a current-item read — a paper truly in two beats shows one. **Task 3 must resolve this**: beats belong to the *item*, unioned across every source that carried it, not to whichever row wrote last.

**`item_type` is deliberately crude.** M1 assigns it from source tier, a government-primary list, and a word count, and says so. M2 owns refining it, and `press` is the churn bucket that must be suppressed in both views.

**The AP corpus is heavy on sports and Spanish-language wire copy.** §4's suppression list for US news names sports, entertainment, opinion, and horse-race polling explicitly. This is the concrete test of whether the interest profile works.

## Hard overrides — and two that have no source

§5 pins six categories to the top regardless of computed score. Their status after M1:

| Override | Status |
| --- | --- |
| CISA KEV catalog entries | ✅ ingesting |
| CVE above CVSS threshold | ✅ via `nvd-cve` |
| Juniper SIRT advisories | ❌ **no feed exists** — wishlisted |
| NWS/NHC alerts for my area | ❌ **`api.weather.gov` disallows its whole host** |
| 8-K from a held name | ⏳ M4b |
| Earnings within 5 sessions | ⏳ M4b |

Two of six are unreachable, and one of those is hurricane warnings during season. **Implement the override mechanism generically** so a source becoming available later is a config change, not a code change — and record the two gaps in the report rather than silently implementing four of six.

## Tasks

Waves are barriers; tasks within a wave touch disjoint files and run in parallel.

### Wave 1 — foundations (parallel)

**Task 1 — Interest profile.** `config/interests.yaml` + `src/interests/load.ts`. Zod-validated boost and suppress terms with weights. Seed boosts from §5: `prompt injection`, `MCP`, `agent security`, `Juniper`, `Junos`, `BGP`, `network automation`, `local inference`, `Ollama`, `eval`, `RAG`. Seed suppressions: funding rounds, "X launches AI-powered Y" press releases, listicles, crypto — **plus** the §4 US-news list: sports, entertainment, opinion/editorial, horse-race polling. Matching must be case-insensitive, whole-word or phrase, and must not match inside a longer word.

**Task 2 — Recency decay.** `src/score/decay.ts`. A pure function of `publishedAt`, `now`, and a half-life. Half-lives per `item_type` for markets and per beat elsewhere, from config not constants. **A null `published_at` must have defined behaviour** — decide it, justify it, and test it, because M1 proved nulls are real.

**Task 3 — Item beats union.** `src/domain/itemBeats.ts`. Resolve the arXiv shadowing: a read must return every beat any source attributed to the item, not the last writer's. Prove it with the real cross-listing case.

### Wave 2 — clustering (single task, needs Wave 1's beats fix)

**Task 4 — Near-duplicate clustering.** `src/cluster/`. Trigram Jaccard over normalized titles, threshold configurable. Exact `canonical_url` matches are already one `item_key` and need no clustering. Writes `clusters` and `item_clusters`, both append-only and `fetched_at`-stamped so cluster size is reconstructible at any past instant — that stamping already exists in the schema and must be honoured. Prefer under-clustering: merging two genuinely different stories is worse than missing a duplicate, and the threshold should be justified against real M1 titles.

### Wave 3 — scoring (parallel)

**Task 5 — Mechanical scorer.** `src/score/mechanical.ts`. Combines source trust weight, cluster size, and interest matches into the decay-invariant components for both `signal_score` and `read_score`. Portfolio proximity is an explicit no-op stub until M4b — named, tested as a no-op, not silently absent.

**Task 6 — Hard overrides.** `src/score/overrides.ts`. Generic mechanism, config-driven, with the two unreachable categories recorded rather than faked.

**Task 7 — `item_type` refinement.** Replaces M1's crude rule. `press` becomes a real churn classifier suppressed in both views.

### Wave 4 — proof and wiring

**Task 8 — Golden-file scoring test.** §6 requires this explicitly: a checked-in corpus with expected rankings, so a scoring change shows up as a reviewable diff. **Derive expectations from the rules, not by running the scorer** — M1 proved a fixture generated from its own implementation cannot catch a bug baked into its oracle.

**Task 9 — Scoring pass + CLI.** A pass that scores unscored items, invocable independently of ingest. Rescoring must not require refetching.

## M2 Acceptance

Ingest a fresh corpus, run the scoring pass, and query the top items per beat. **The deliverable is a judgement call, not a number**: are they the ones I would have picked? Specifically — is the AP sports and Spanish-language copy gone from US news, does a multi-source story outrank a single-source one, and does a CISA KEV entry pin to the top regardless of everything else?

**Not in M2:** no API beyond `/health`, no frontend, no enrichment, no vault, no MCP, no markets sources, no GitHub lane.
